# Chop — پنل مدیریت VLESS روی Cloudflare Workers

## این چیه؟

پورت کامل پروژه‌ی Chop (که قبلاً برای Vercel نوشته شده بود) به **Cloudflare
Workers**. همون پنل مدیریت کانفیگ + همون ریلی VLESS+WS، ولی این‌بار روی
معماری Workers:

| قبل (Vercel) | حالا (Cloudflare Workers) |
|---|---|
| FastAPI (پایتون) | Worker با فچ-هندلر (جاوااسکریپت، بدون فریم‌ورک) |
| Redis (Upstash) برای ذخیره‌سازی | **Durable Object** با استوریج SQLite داخلی |
| `asyncio.open_connection` برای اتصال خروجی | `connect()` از `cloudflare:sockets` |
| WebSocket با Fluid Compute | WebSocket بومی Workers (`WebSocketPair`) |
| مسیر legacy `XHTTP` (`/x`) با صف Redis | **حذف شده** — دیگه لازم نیست، پایین توضیح داده شده |

## چرا معماری عوض شد (نه فقط ترجمه‌ی خط‌به‌خط)

نسخه‌ی Vercel به‌خاطر دو محدودیت پلتفرم آن‌جا، از Redis استفاده می‌کرد:
(۱) فایل‌سیستم/حافظه‌ی هر instance موقتی بود، و (۲) مسیر legacy XHTTP نیاز
داشت درخواست‌های آپلود/دانلود جدا رو از طریق یک صف بین‌پروسه‌ای به هم وصل کنه.

روی Cloudflare Workers معادل درستِ همون نیاز یک **Durable Object** است: یک
شیء تکی که storage آن native و strongly-consistent است (بدون نیاز به سرویس
خارجی مثل Upstash) و همه‌ی درخواست‌ها (پنل، ربات تلگرام، چک کوتا/IP در ابتدای
هر اتصال VLESS) به همون یک نمونه می‌رسند. کدش در `src/store.js` است و همون
عملیات‌های `storage.py` (لیست/ذخیره/حذف کانفیگ، مصرف، آنلاین‌بودن، لاگ، تنظیمات
ربات، بکاپ/بازیابی) رو با متدهای RPC مستقیم پیاده می‌کنه.

مسیر legacy XHTTP هم به‌طور کامل حذف شده: همون مشکلی که اون مسیر حل می‌کرد
(پین‌نشدنِ session به یک instance) روی Workers با WebSocket بومی از اول وجود
نداره، پس نگه‌داشتنش فقط پیچیدگی اضافه بود.

## محدودیت‌های واقعی (صادقانه بخون)

- **اتصال خروجی TCP (`connect()`) به چند مقصد اجازه داده نمی‌شه**: پورت ۲۵
  (SMTP)، آی‌پی‌های خودِ Cloudflare، آدرس‌های localhost/شبکه‌ی خصوصی، و
  اتصال یک Worker به خودش. این‌ها محدودیت‌های ثابت پلتفرم‌اند، نه چیزی که
  این پروژه اضافه کرده باشه. بقیه‌ی مقصدها (از جمله پورت ۴۴۳ که کلاینت‌های
  VLESS معمولاً استفاده می‌کنن) مشکلی ندارن.
- **تعداد سوکت‌های TCP هم‌زمان باز محدوده** (طبق پلن Workers). زیر بار خیلی
  سنگین ممکنه به این سقف بخوری؛ جزئیات دقیق فعلی رو از
  [مستندات TCP Sockets](https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/)
  چک کن.
- **تست محلی (`wrangler dev`) اتصال TCP خروجی واقعی رو کامل شبیه‌سازی نمی‌کنه.**
  برای تست واقعیِ ریلی VLESS، یا مستقیم دیپلوی کن، یا `wrangler dev --remote`
  رو امتحان کن.
- **Durable Objects روی پلن رایگان Workers هم در دسترسن** (با استوریج
  SQLite)، اما سقف مصرف (تعداد درخواست/GB-second) دارن؛ برای یک پنل شخصی با
  چند ده کاربر معمولاً کافیه. جزئیات به‌روز:
  [Workers Pricing](https://developers.cloudflare.com/workers/platform/pricing/).
- برای هر کانفیگ، تشخیص UUID با اسکن کامل لیست کانفیگ‌ها انجام می‌شه (نه
  ایندکس جدا) — برای مقیاس یک پنل شخصی (چند ده تا چند صد کانفیگ) این کاملاً
  کافیه؛ اگه قراره هزاران کانفیگ همزمان داشته باشی، بهتره یک ایندکس
  UUID→id جدا اضافه کنی.
- مصرف ترافیک واقعی کاربرها از سهمیه‌ی درخواست/CPU-time پلن Workers شما کم
  می‌شه. زیر بار سنگین ممکنه هزینه بره بالا یا نرخ‌محدود بشی.
- این پروژه یک ابزار پروکسی/VPN شخصی است. اگه کانفیگ‌ها رو بین چند نفر پخش
  می‌کنی، مسئولیت رعایت قوانین محلی و شرایط استفاده‌ی Cloudflare با خودته.

## مرحله ۱: نصب ابزارها

```bash
npm install -g wrangler   # یا از npx استفاده کن
wrangler login
```

## مرحله ۲: تنظیم متغیرهای محیطی (secrets)

```bash
cd chop-worker
wrangler secret put ADMIN_USER      # مثلاً admin
wrangler secret put ADMIN_PASS      # یک رمز قوی
wrangler secret put SESSION_SECRET  # رشته‌ی تصادفی، مثلاً: openssl rand -hex 32
```

(`ADMIN_USER` در `wrangler.toml` هم یک مقدار پیش‌فرض داره؛ اگه به‌صورت secret
ستش کنی همون اولویت داره.)

## مرحله ۳: دیپلوی

```bash
npm install
wrangler deploy
```

اولین دیپلوی، Durable Object namespace (`ChopStore`) رو خودکار می‌سازه —
نیازی به ساخت دستی چیزی در داشبورد نیست.

## مرحله ۴: استفاده

- وارد `https://<your-worker>.<your-subdomain>.workers.dev` شو با
  `ADMIN_USER`/`ADMIN_PASS`.
- از داشبورد یک کانفیگ جدید بساز (نام، محدودیت ترافیک، محدودیت آی‌پی، پورت،
  fingerprint، ALPN).
- لینک `vless://` تولیدشده از نوع `type=ws` است؛ با یک کلاینت Xray-core
  به‌روز (v2rayNG، NekoBox، Streisand) با ترنسپورت **WebSocket** تست کن.
- اگه دامنه‌ی سفارشی روی Worker وصل کردی، لینک‌ها به‌طور خودکار از هاست
  همون درخواست ساخته می‌شن؛ اگه می‌خوای هاست ثابتی در لینک‌ها بیاد (مثلاً
  پشت چند دامنه)، متغیر `PUBLIC_HOST` رو ست کن.

## فایل‌ها

| فایل | نقش |
|---|---|
| `src/index.js` | روتر اصلی Worker: auth، API مدیریت کانفیگ، صفحات، webhook بات |
| `src/wsrelay.js` | موتور ریلی VLESS+WS (WebSocketPair + `cloudflare:sockets`) |
| `src/vless.js` | پارس/ساخت هدر پروتکل VLESS |
| `src/store.js` | Durable Object — لایه‌ی ذخیره‌سازی (جایگزین Redis) |
| `src/authcookie.js` | کوکی سشن امضاشده (HMAC-SHA256 با Web Crypto) برای ورود ادمین |
| `src/ui.js` | HTML/CSS/JS پنل (بدون نیاز به build جدا) |
| `src/bot.js` | منطق ربات تلگرام (webhook، منوی دکمه‌دار، مدیریت اعضا/ادمین) |
| `wrangler.toml` | تنظیمات دیپلوی و binding مربوط به Durable Object |

## قابلیت‌های پنل

همه‌ی قابلیت‌های نسخه‌ی Vercel حفظ شده:

- مدیریت کانفیگ (ساخت/ویرایش/فعال‌غیرفعال/حذف) با محدودیت ترافیک، تعداد
  آی‌پی هم‌زمان، انقضا، fingerprint و ALPN دلخواه
- آمار زنده (تعداد کانفیگ، آنلاین، ترافیک کل) و نمودار ترافیک ساعتی
- لاگ اتصال‌ها (فیلتر بر اساس کانفیگ)، با همون سقف ۳۰۰ رکورد به‌ازای هر
  کانفیگ و ۱۰۰۰ رکورد کلی
- ربات تلگرام کامل: منوی مدیریت کانفیگ از داخل بات، ساخت کانفیگ جدید،
  مدیریت ادمین‌ها/اعضا، بکاپ کامل با `/backup`
- بکاپ/بازیابی JSON کامل (جایگزینی کامل یا ادغام)، از پنل یا از بات

## راه‌اندازی ربات تلگرام

1. با @BotFather یک بات بساز و توکنش رو بگیر.
2. وارد پنل شو → تب **«ربات تلگرام»** → توکن رو بچسبون → تیک «فعال باشه»
   رو بزن → **«ذخیره و اتصال Webhook»**.
3. برای اولین ادمین بودن: به بات پیام بده، `/id` رو بفرست، آی‌دی عددی رو
   در پنل (تب «ربات تلگرام») اضافه کن.
4. از اون به بعد با `/start` یا `/admin` منوی مدیریت در دسترسه؛ ادمین‌های
   دیگه هم با `/addadmin <آی‌دی عددی>` قابل افزودنن.
